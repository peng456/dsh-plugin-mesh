# T · trace 子路线图（观测图）

> 父文档：[`ROADMAP.md`](../../ROADMAP.md) §2 · 被 [`R-v1`](./route.md) 闸住。
> **只做观测图，不做编排图**（决策 D2）。

**回答什么**：这件事什么时候、在哪台、做了什么、结果如何？

**一个必须先说清的边界**：`trace` 不是分布式 tracing 系统（不是 OpenTelemetry）。
它只有一个数据源 —— **任务事件流**；也只有一种渲染 —— **状态时间线**。
凡是要「调度下一步」的东西，都属于编排，本方向不做。

---

## 现状（v0）

**无**。全仓 `trace` 零命中。今天的「流转」只能靠人翻任务列表 + 回忆对话。

## T-v1 · 时间线（单机）

| 项 | 设计 |
|---|---|
| 数据源 | 只读 `GET /mesh/v1/events`，不新增埋点 |
| 单元 | 一张工单的一次跳（hop）：`{ taskId, parentTaskId?, host, phase, ts, evidence }` |
| 渲染 | 状态迁移序列：`queued 10:01 → running 10:02 → completed 10:05`，每步展开证据（命令 / 退出码 / 改了哪些文件） |
| 入口 | 面板任务详情；CLI `mesh tasks <id> --timeline` |

**验收**：四问可答 —— 什么时候、在哪台、做了什么、结果如何；一次跳的证据自足（不需要再问对端）。

---

## T-v2 · 串链（跨机）

| 项 | 设计 |
|---|---|
| 串联键 | `conversationId`（两端各自算，不协商 —— 已有机制） |
| 形态 | 一条链 = 一次委派的全部跳；A→B→C 各自一段，可折叠 |
| 诚实边界 | 现网拓扑基本是 A→B 一条边，多跳在观察区 → **今天画出来大概率是一根线** |
| 失败处理 | 断链要**显式标注**「这一段不知道」，不能把缺失拼成完整时间线 |

**验收**：跨机任务链可展开；缺失段显式标注而不是静默补全。

---

## T-v3 · 流转图（条件触发）

**前置**：观察区的多跳转派（深度 ≤2 + 预算 + 来源链）真的落地。

**做法**：把 T-v1/v2 的时间线渲染成图（节点 = 机器，边 = 一次跳）。
**图是渲染方式，不是新数据源** —— 不引入采样、不引入 traceId 体系、不要求对端改协议。

**验收**：图上的每条边都能点回时间线的具体一跳。

| 关系 | 说明 |

| **入** | T-v1 需要 [`R-v1`](./route.md) 的事件流；T-v3 需要观察区的多跳 |

## 边界

- 不做编排图 / DAG / 调度（与「不做工作流引擎」冲突）
- 不做通用 tracing（不接 OTel，不做采样）
- 不做「应该发生什么」的推演图 —— 只画已发生
