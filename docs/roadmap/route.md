# R · 会话事件智能路由 子路线图

> 父文档：[`ROADMAP.md`](../../ROADMAP.md) §2 · 本方向是多数交付方向的**共同前置**。
> 设计细节：[`../design/任务追踪设计.md`](../design/任务追踪设计.md)

**回答什么**：这张工单跑到哪了？谁在做？做完了吗？为什么选这台？

**名字就是结构**——三个词对应三层，越往下越不确定：

| 词 | 层 | 内容 | 确定性 |
|---|---|---|---|
| **事件** | L1 | 调用事件流模型 + 任务流水账（journal） + 结果信封 + 取消 | 纯确定性，无模型 |
| **会话** | L2 | `thread → (host, sessionId, 状态)` 唯一持有 + 续跑串行化 | 规则 |
| **智能路由** | L3 | `requires` → 在线 → 负载 → 通道 → 成功率；同分才问模型 | 规则优先，模型后置 |

---

## 现状（v0）

| 缺口 | 证据 |
|---|---|
| 无状态机 | 状态是散落字符串：`dispatched` / `injected-thread-session` / `noted-only` / `queued-for-session` / `dispatch-failed`；派出记录直接是 HTTP `200` |
| 无取消 | `lib/` 全目录 `cancel` 零命中 |
| 无结果契约 | 结果是「对端 agent 再调一次 `mesh_run` 回派的一段文本」 |
| 无事件流 | `lib/` 内无 `text/event-stream` / `EventSource` |
| 无会话账本 | `thread → session` 的映射谁都能算，没有唯一持有者 |
| 无放置 | `placement` 仅出现在文档与能力采集注释里 |

**真实代价**：41 条账本里 21 条派出任务状态是 `200` / `undefined`，同一句探针被手工发了 6 次；
一次 `status: undefined` 至今无法判断到没到。

## R-v1 · 调用事件流模型重构 + journal + 信封 + 取消（L1，纯确定性）

| 工作项 | 做到什么 |
|---|---|
| **调用事件流模型重构** | 把「一次派发 = 一个 HTTP 请求」改成「一次派发 = 一条可追踪的调用记录 + 有序事件」；`index.js` 里散落的状态字符串收敛为状态机；事件流（SSE）是这条模型的传输，不是附加功能 |
| 任务 journal | `mesh/tasks.json` 状态机；**迁移不是重写**（保住 200 条上限 / 4KB 截断；旧记录允许 `unknown`） |
| 事件流 | `GET /mesh/v1/events`（SSE + `since` 游标），8 类事件 |
| 结果信封 | `{ conversationId, status, summary, evidence{commands, exitCodes, filesChanged}, artifacts[], error }` |
| 取消 | `POST /mesh/v1/tasks/:id/cancel`，回执明确「已停」/「太晚，已终态」 |
| 终态通知 | ~~归 U-v1~~ —— 本方向只负责产出终态与事件，**展示归 [`U-v1`](./ui.md)** |

```
queued → running → waiting-input → completed / failed / cancelled
                               └→ unknown（旧记录 / 对端无终态能力）
```

**验收**：重启后状态可恢复且旧记录不丢 · `curl -N` 见 8 类事件 · 断线重连不重复 ·
旧对端只读到 `summary` 也不崩 · 取消确认率 100% · **一次派发在账本里是一条记录，不再是一个 HTTP 码**。

**刻意不做**：不碰 UI、不接新宿主、不做放置、不接模型。

**风险**：`tasks.json` 已有 `persist.js`（200 条 / 4KB 截断），必须迁移不能重写；
旧记录没有终态，`unknown` 是合法状态，不是错误。

## R-v2 · 会话账本（L2，规则）

| 要回答 | 今天答不了 |
|---|---|
| 这个 `thread` 绑在哪个宿主的哪个 session 上？ | 没有唯一持有者 |
| 两个进程同时续跑同一 session，谁赢？ | 没有串行化，两边都以为在写同一份上下文 |
| 宿主重启后 `sessionId` 还能不能续？ | 没有映射，续跑等于新开会话 |

**工作项**：节点唯一持有 `thread → (host, sessionId, 状态)`；按 thread 加锁，第二个续跑请求
排队而非并行；重启后可恢复映射。

**验收**：并发续跑下上下文不互相覆盖；重启后续跑命中同一 session。

## R-v3 · 路由（L3，规则优先，模型后置）

| 工作项 | 做到什么 |
|---|---|
| `requires` 最小语法 | 包含某运行时 / OS / GPU；`runtimesIncomplete: true` 的设备**不得用于硬门槛排除** |
| 规则路由器 | 硬门槛 → 在线 → 负载 → 通道 → 历史成功率 |
| 放置留痕 | `placementDecision`：选了谁、排除了谁、为什么 |
| 自动放置 | `peer:"auto"` 显式开，**默认关** |
| 模型层（条件触发） | 仅同分候选时调用，输出理由不执行 |

**三条不变量**

1. 显式声明 > 系统推断（`peer="mac"` 永远胜过算法偏好）
2. 规则层永远在线，模型层永远可关
3. 同分才问模型，模型只给理由不执行

**验收**：规则层命中率 ≥80%（**没有 R-v1 的账本就算不出来**）· 误放置率 <2% ·
关掉模型 conformance 全绿 · 能力不足时明确失败、不静默改派。

## 闸门

| 方向 | 关系 |
|---|---|
| **出** | R-v1 闸住 [`T-v1`](./trace.md) / [`U-v1`](./ui.md) / [`P-v1`](./play.md)；R-v3 被 R-v1 的数据闸住 |
| **入** | 无。R-v1 可以立刻开始 |

## 边界

- 不做多跳转派（观察区，深度 ≤2 + 预算 + 来源链）
- 不做工作流引擎 / DAG 编排
- 不做模型兜底一切（D4：关掉模型必须仍能选机器）
